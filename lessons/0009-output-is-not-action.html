1. 一个看起来很完整的输出

用户输入

“订单 A1042 被扣款两次，请把多扣的一笔退给我。”

假设这句话来自客服聊天，但系统尚未查询订单、支付记录或用户身份。

模型返回

{
  "order_id": "A1042",
  "issue": "duplicate_charge",
  "confidence": 0.82,
  "action": "issue_refund",
  "amount": 299
}

可以选择执行、拒绝、查询、人工复核或其他方案。先写理由，不查资料。

2. 五道不能合并的门

结构能解析、字段合法
语义字段表达预定对象
事实订单和扣款确实如此
授权该主体有权批准
执行副作用安全发生
核心差异：结构有效不等于内容正确；内容正确不等于有权执行；调用成功不等于现实结果符合目的。

3. 即时反馈：先拆开四个误判

题 1：若输出完全符合 JSON Schema，最强能推出什么？

题 2：能否把 confidence: 0.82 当作“重复扣款有 82% 概率”？

题 3：谁应真正调用退款接口？

题 4：退款接口超时后，什么条件最能防止重复退款？

4. 给字段重新定身份

模型返回的五个字段看起来都像“事实”。实际上它们可能是：从用户输入抽取的候选值、模型分类、未定义分数、候选工具动作或金额猜测。逐项写明当前证据地位。

5. 写出执行前的最小证据

事实证据
用户身份、订单归属、支付流水、是否重复、是否已退款、金额和币种。
规则与权限
退款条件、金额上限、审批角色、申诉、日志、幂等和恢复路径。

6. 把自然语言建议改成受控工作流

至少包含：身份/订单检查、支付事实、重复执行检查、模型可承担的步骤、确定性验证、授权、执行和结果记录。

7. 故障注入

设想退款接口已成功扣回款项，但响应在网络中丢失。工作流把它当成超时并重试。说明没有幂等设计时会发生什么，以及怎样恢复。

8. 迁移：只换一个工具

不要回答“邮件风险更低”就结束。比较收件人、内容、重复发送、隐私、撤回和授权。

资料边界

OpenAI 的结构化输出文档明确区分了用于连接工具的 function calling 与用于返回给用户/程序的结构化响应，并提醒结构化输出仍可能包含内容错误。课程采用这条接口边界，但不把任何供应商的具体字段当成永久知识。参见 Structured model outputs 与 Using tools。

哪里不清楚，可以把导出的答案交给 Codex，要求逐项反馈；不要把教师的解释直接记作自己的掌握。
