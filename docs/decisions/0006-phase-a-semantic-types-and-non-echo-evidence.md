# 0006：阶段 A 先建立量的语义类型，再取得非回显证据

## 状态

已接受，2026-08-18。

## 背景

阶段 A 已经建立了“现实含义 → 程序责任 → 代码位置 → Python 写法 → 学生操作 → 运行验证”的翻译层，但 retry 会话暴露出更细的缺口：`attempt`、重试次数、执行上限、等待时长、是否等待和等待策略虽然都出现在页面上，却没有先声明各自的语义类型、单位和变化时机。页面还把一般策略计算出的候选等待时长与具体运行中实际发生的等待放在相邻题目里，容易让学习者把两个层次合并。

另一个问题是答案回显：题干已经写出 `1、2、4`，后续再用 `1/2/4` 选择框要求回填，检查器可以得到“正确”，但没有证明学习者提取了规律或理解了停止条件。

## 决定

阶段 A 的所有连续过程题遵循以下协议：

1. 每个量先标明含义、单位/类型、变化时机、改变者和影响步骤；例如 `attempt` 是执行序号，`delay` 是下一次执行前的抽象时间长度。
2. 过程先用普通语言展开为“执行 → 成功/失败 → 判断是否还有下一次 → 若有则计算候选值 → 产生副作用 → 下一次执行”，再进入 Python。
3. 页面明确区分“是否等待”和“如果等待，等待多久”；前者属于控制流和停止条件，后者属于等待策略。
4. 页面明确区分一般策略函数的候选值和具体运行实际调用的副作用。候选值可以存在，但没有下一次执行机会时不产生等待调用。
5. 每个可操作的小题只设置一个主要未知量；一个有界变化如果需要多个证据，按顺序解锁。已经给出的规律不得通过同答案选项回显；新的任务应使用未见案例，例如从 `1、2、4` 推出下一项，或判断 `max_attempts=4` 的最后一次是否真正等待。
6. 选择题的错误选项必须对应可解释的错误模型；否则改用自由填写、trace 预测或运行证据。
7. 阶段 A 后半段逐步把证据重心从 Python 语法回忆转向代码地图、控制流/数据流、测试/traceback 诊断、局部修改和未见条件验证。

## 未采用的方案

- **只把“等待值”改名：**名称改善不能替代单位、过程时序和策略/轨迹分层。
- **把 `max_attempts` 改成更大的数字就结束：**更大的示例可以让候选等待真实发生，但不能解决一般策略和具体运行没有分层的问题。
- **继续保留 1、2、4 的逐项选择：**它优化自动检查，不产生规律抽象或停止条件的证据。
- **把语法记忆当作代码所有权：**真实所有权需要模型、证据、诊断和有界修改，API 记忆可以由查询工具补足。

## 后果

- 当前正式会话 2 的三道题需要整体重写，而不是只替换 retry 任务的一行文案；七步闭环、九项任务和页面路径接口保持不变。
- 页面会增加量定义、时序表、候选值/实际副作用说明和新案例输入，题面比原来更长，但答错后能定位到具体认知层。
- 后续阶段 A 会复用“语义类型 + 唯一未知量 + 非回显证据”的出题审查表，并逐步减少定位和语法帮助。
